# Contributing to QuickBuds

Thanks for helping. The most useful contribution is **a report from an owner of earbuds other than
the OnePlus Buds 4**. The writes for every other model come from HeyMelody's and realme Link's data.
Owners have confirmed only the realme Buds Air7 Pro and the OPPO Enco Buds2. Code contributions are
welcome too.

## Reporting a model

The quickest way is in the app: Settings › **Test my earbuds** (desktop: App settings). Mark each
feature as works, does not work or skip, then tap Send. The report holds a fresh log, without Bluetooth
addresses. Settings › **Report a problem** sends one problem with your description. For a longer exchange, open an
[issue](https://github.com/spizganed/QuickBuds/issues) with:

1. The earbuds' model, and the phone or PC it runs on (model, Android / Windows / Linux version).
2. What works and what does not. "The switch flips but nothing changes on the buds" is useful.
3. A log: in the app, Dev tools › **Clear**, try the features, then Dev tools › **Export**. The file
   lands in `Download/QuickBuds/` (PC: `Downloads/QuickBuds`). Attach it as is.

For anything the app's log does not explain, [PACKET-CAPTURE.md](./PACKET-CAPTURE.md) shows how to
capture the Bluetooth traffic itself, including what HeyMelody sends.

## Tests

```bash
python3 scripts/check-locales.py   # every string in all 26 locales
cd core && cargo test              # the core crate tests (frames, messages, commands)
cd desktop && cargo test           # the desktop tests, including core against protocol.rs
./gradlew :app:testDebugUnitTest  # the Android protocol tests (app/src/test)
```

`scripts/release-build.sh` runs every check of the Build workflow and builds all release files. It
needs the release key. Without the key, run the two commands above.

## Translations

Strings are in `app/src/main/res/values/strings.xml` (English) and one `values-<code>/strings.xml`
per locale. The desktop app uses the same files. A fix to a translation is welcome as a pull request.
A new string needs all 26 locales. Machine drafts are fine.

## Where things are

One module, `:app`, sources in `app/src/main/kotlin/com/spizganed/quickbuds/`:

| Package | What it holds |
|---|---|
| `bluetooth/` | The RFCOMM link, reconnects, the packet log (`BudsConnectionManager`, `BudsService`) |
| `protocol/` | Packet building and parsing (`OpoProtocol`, the parsers) |
| `ui/` | Activities, custom views, theming |
| `widget/` | Home screen widgets (layouts generated by `scripts/widget-layouts.py`) |

The desktop app is `desktop/`. It uses the `core/` crate (`buds-core`: frames, typed messages, commands).
Each protocol has one file that the rest of the code calls:

| File | Role |
|---|---|
| `src/newproto.rs` | The new protocol: frames out and in, answers and the `buds_core` message to `Event` map |
| `src/protocol.rs` | The legacy protocol: framing, decoders, answers, old builders (also the reference of the core tests) |
| `src/proto.rs` | The selector (`Proto::New` or `Proto::Legacy`). `session.rs` calls it and never branches on the protocol |
| `src/types.rs` | What both share: ids, `Event`, `Caps`, model data, log frames, the packet log's text |

Other files: `src/session.rs` (the link), `src/bt.rs` (Bluetooth sockets), `ui/app.slint` (the UI).

The new protocol is the default on desktop. `proto.rs` sends with `buds_core::wire` and reads with `buds_core::msg`;
`session.rs` builds its frames with `buds_core::cmd`. A differential test in `src/core_tests.rs` proves each builder against `protocol.rs`.
Settings › **Legacy protocol** (`protocol_legacy` in `settings.json`) selects the old link. When the buds
send nothing on the new link, the app stores `<address>|<version>` in `protocol_fell_back`
and uses the old link for these buds until the next app version.

Per-model data (features, noise control modes, EQ presets, gestures) is in
`app/src/main/assets/models.json`. Our own key `confirmed` lists the features an owner confirmed
(`ModelTest.FEATURES` keys). A model whose list covers every feature the app shows gets no test prompt.

Read before changing anything:

- [PROTOCOL.md](./PROTOCOL.md): the wire format. Every claim is tagged with its source.
- [ROADMAP.md](./ROADMAP.md): the plan, and the list of features decided against. Please check that
  list before proposing a feature.

## Rules that matter

- **Never guess a payload or a command number.** A wrong write to the buds fails silently. Capture
  what HeyMelody sends first ([PACKET-CAPTURE.md](./PACKET-CAPTURE.md)), then read the result back.
- **Docs change with the code.** A protocol change comes with its PROTOCOL.md entry in the same commit.
- **A new user-visible string needs all 26 translations** (`app/src/main/res/values-*`). Machine
  drafts are fine. Lint does not catch a missing one; `scripts/check-locales.py` does, and the Build workflow runs it.
- No new dependencies in the Android app, no Material Components. Every activity is portrait-locked by hand.
- Widget layouts are generated: edit `scripts/widget-layouts.py` and rerun it, never the XML.
- Test on real buds and say which model and firmware in the pull request.
- No vendor code, class names or file names in the repo, only the bytes on the wire.

## Pull requests

Fork, branch from `main`, keep one change per pull request, and describe what you tested on which
buds. The project is GPL-3.0-or-later; contributions are accepted under the same license.
